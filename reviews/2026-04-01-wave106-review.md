## TSContractSystemManager.h — CONCERNS

### Issues Found

1. **[Major] `#include "Net/UnrealNetwork.h"` in header** — Line: 7 — The UnrealNetwork header is only needed in the .cpp for `DOREPLIFETIME` macros. Including it in the header pollutes the include chain for every file that includes this header. **Fix:** Move `#include "Net/UnrealNetwork.h"` to the .cpp file only.

2. **[Minor] No dedicated log category** — Lines: 62, 69, 75, 96, etc. — All logging uses `LogTemp`. Production code should define a `DECLARE_LOG_CATEGORY_EXTERN` / `DEFINE_LOG_CATEGORY` pair (e.g., `LogTSContract`) for filterable logging. **Fix:** Add `DECLARE_LOG_CATEGORY_EXTERN(LogTSContract, Log, All)` in the header and define it in the .cpp.

3. **[Minor] `GetActiveContracts()` returns by value** — Line: 169 — Returns `TArray<FTSContractData>` by copy. For a query function called potentially every frame from UI, this is an unnecessary allocation. **Fix:** Return `const TArray<FTSContractData>&` instead.

4. **[Minor] FTSContractData fields are all `EditAnywhere, BlueprintReadWrite`** — Lines: 40-85 — `CurrentProgress`, `bIsActive`, `bIsCompleted`, `bIsClaimed` are runtime state that designers should not edit. Exposing them as `EditAnywhere` invites data corruption in Blueprint defaults. **Fix:** Use `VisibleAnywhere, BlueprintReadOnly` for runtime state fields, keep `EditAnywhere` only for config fields like `TargetValue`, `Tier`, etc.

5. **[Minor] No authority check on mutating functions** — Lines: 142-160 — `AcceptContract`, `AbandonContract`, `ClaimReward`, `UpdateProgress` are `BlueprintCallable` but have no `HasAuthority()` guard or Server RPC wrapper. Any client can call these directly, bypassing server authority. **Fix:** Either make these `Server, Reliable` RPCs, or add `if (!GetOwner()->HasAuthority()) return;` guards and provide separate Server RPC entry points.

6. **[Minor] `IsExpired()` inline in header struct** — Line: 88-92 — This is fine for a small function but the logic uses world time directly, which could diverge between client/server. **Fix:** Document that `StartTime` and `CurrentWorldTime` must be server-authoritative.

### Positive Notes
- Clean F-prefix struct naming (`FTSContractData`, `FTSContractBoard`) and U-prefix component naming.
- `#pragma once` and `.generated.h` correctly placed.
- Well-documented with Doxygen-style comments on every public function.
- `MaxBoardSlots` and `MaxActiveContracts` are `constexpr` — no magic numbers.
- Delegates are properly declared as `DYNAMIC_MULTICAST` for Blueprint compatibility.
- `FGuid` for contract identification is a solid choice — avoids integer ID collisions.
- `SaveGame` specifier on persistent properties shows forward-thinking serialization design.

### Score: 7/10

## TSContractSystemManager.cpp — CONCERNS

### Issues Found

1. **[Critical] Broken shuffle algorithm** — Lines: 213-216 — The sort lambda uses `FMath::RandHelper(2) == 0` which produces a non-deterministic comparator that violates strict weak ordering. This is **undefined behavior** in C++ and can cause crashes or infinite loops in sorting implementations. The `Seed` variable on line 212 is captured but never used. **Fix:** Use `FMath::RandRange` with proper Fisher-Yates shuffle:
   ```cpp
   for (int32 i = ShuffledPool.Num() - 1; i > 0; --i)
   {
       int32 j = FMath::RandRange(0, i);
       ShuffledPool.Swap(i, j);
   }
   ```

2. **[Major] `SaveContracts()` and `LoadContracts()` are stubs** — Lines: 238-249 — These are no-ops that only log. The `SaveGame` UPROPERTY specifier alone does NOT persist data — it only marks fields for serialization. Without actual `USaveGame` subsystem integration, no data persists across sessions. The comment "SaveGame-marked properties are automatically serialized" is misleading. **Fix:** Implement actual save/load using `UGameplayStatics::SaveGameToSlot` / `LoadGameFromSlot`, or clearly mark these as `// TODO` with a tracking ticket.

3. **[Major] `UpdateProgress` saves on every single progress increment** — Line: 195 — Every kill, headshot, etc. triggers `SaveContracts()`. Even though SaveContracts is currently a stub, once implemented this will be a performance bottleneck with disk I/O on every gameplay event. **Fix:** Use a dirty flag and save on a timer or at natural breakpoints (round end, match end).

4. **[Minor] `AcceptContract` modifies board contract then copies** — Lines: 80-85 — The code modifies `BoardContract` in-place (setting `bIsActive`, `CurrentProgress`, `StartTime`) before copying it. If `RemoveAll` on line 88 fails or is skipped, the board now contains a corrupted entry marked as active. **Fix:** Copy first, modify the copy, then remove from board.

5. **[Minor] Duplicate include** — Line: 3 vs Header Line 7 — `Net/UnrealNetwork.h` is included in both the header and the .cpp. **Fix:** Remove from header (see header issue #1).

6. **[Minor] `CheckExpiredContracts` does not save** — Lines: 253-266 — When a contract expires and is removed, `SaveContracts()` is not called. This is inconsistent with other state mutations that do call save. **Fix:** Add `SaveContracts()` after the expiry loop if any contracts were removed.

### Positive Notes
- Correct reverse iteration in `CheckExpiredContracts` when removing elements.
- `TickInterval = 1.f` is appropriate — no need for 60Hz contract checking.
- `GetLifetimeReplicatedProps` and `DOREPLIFETIME` properly implemented.
- `SetIsReplicatedByDefault(true)` correctly set in constructor.
- Good guard clauses and early returns throughout.
- `FindContractByID` helper avoids code duplication.

### Score: 6/10

## TSMedalSystemManager.h — PASS

### Issues Found

1. **[Minor] `#include "Net/UnrealNetwork.h"` in header** — Line: 7 — Same issue as ContractSystem. Only needed in .cpp. **Fix:** Move to .cpp.

2. **[Minor] `#include "Engine/Texture2D.h"` in header** — Line: 8 — Since `MedalIcon` uses `TSoftObjectPtr<UTexture2D>`, a forward declaration `class UTexture2D;` suffices. Including the full header is unnecessary. **Fix:** Replace with forward declaration.

3. **[Major] `CheckForMedals` has 18 parameters** — Lines: 165-184 — This is a code smell. The function signature is brittle, hard to maintain, and error-prone at call sites. Any new medal type requires changing the signature. **Fix:** Introduce an `FTSCombatEventContext` struct to bundle all combat state, and pass that single struct instead.

4. **[Minor] `GetMatchMedals()` returns by value** — Line: 197 — Same copy issue as ContractSystem. **Fix:** Return `const TArray<FTSMedalEarnedEvent>&`.

5. **[Minor] No authority checks on `AwardMedal`** — Line: 188 — `AwardMedal` is `BlueprintCallable` with no server authority guard. A cheating client could award arbitrary medals. **Fix:** Add authority check or make it a Server RPC.

6. **[Minor] `CurrentMatchID` and `CurrentRoundNumber` are `BlueprintReadWrite`** — Lines: 246-250 — These are sensitive state that should be server-controlled, not writable from any Blueprint. **Fix:** Use `BlueprintReadOnly` and provide setter UFUNCTIONs with authority checks.

- `PrimaryComponentTick.bCanEverTick = false` — event-driven design, no unnecessary tick overhead.

- `FTSCareerMedals` with `TMap<ETSMedalType, int32>` is clean and extensible.
- Milestone system with configurable thresholds is well-designed.
- Three-tier delegate system (standard, rare, milestone) gives UI flexibility.

## TSMedalSystemManager.cpp — CONCERNS

### Issues Found

1. **[Major] `CheckForMedals` can award multiple conflicting medals from a single call** — Lines: 55-162 — A single kill event could simultaneously trigger FirstBlood, WallBang, LongShot, Collateral, and MultiKill. While some combinations are valid (WallBang + LongShot), others may be unintended (e.g., awarding MultiKill when `KillCount >= 3` but those kills happened across the round, not "in rapid succession" as the medal description states). The function has no concept of temporal proximity for multi-kills. **Fix:** Either add a `TimeSinceLastKill` parameter to properly gate MultiKill, or document that callers must only pass rapid-succession kill counts.

2. **[Major] `SaveCareerMedals()` and `LoadCareerMedals()` are stubs** — Lines: 199-209 — Same issue as ContractSystem. No actual persistence. **Fix:** Implement or track as TODO with ticket.

3. **[Minor] `RecordMedalEvent` saves after every single medal** — Line: 258 — Same performance concern as ContractSystem. A single `CheckForMedals` call could award 5+ medals, each triggering a save. **Fix:** Batch saves — save once after `CheckForMedals` completes rather than per-medal.

4. **[Minor] `UpdateRarestMedal` is O(N) on every medal award** — Lines: 261-282 — Iterates all career medal counts and looks up definitions for each. Called on every single medal earned. **Fix:** Cache rarity lookups or only recalculate when a new medal type is first earned.

5. **[Minor] Hardcoded `KillCount >= 5` for Ace** — Line: 63 — Assumes 5v5 format. If team size changes (e.g., 3v3 mode), this breaks. **Fix:** Make the ace threshold configurable or derive from game mode settings.

6. **[Minor] Hardcoded `>= 3` for MultiKill, HeadshotStreak, Teamwork** — Lines: 129, 135, 159 — Same as above. **Fix:** Make thresholds data-driven via medal definitions or a config struct.

7. **[Minor] `InitializeDefaultMedals` uses hardcoded strings** — Lines: 304-321 — FText should use `NSLOCTEXT` or `LOCTEXT` macros for localization support. `FText::FromString` creates non-localizable text. **Fix:** Use `NSLOCTEXT("MedalSystem", "FirstBlood", "First Blood")` pattern.

### Positive Notes
- Clean separation between `CheckForMedals` (evaluation) and `AwardMedal` (execution).
- `RecordMedalEvent` properly updates match log, career stats, and broadcasts in one flow.
- Rare medal delegate fires only for Epic+ rarity — smart filtering for UI.
- `GetMedalDefinition` uses `FindByPredicate` — clean and readable.
- `ResetMatchMedals` generates a new `FGuid` for match tracking — prevents stale data.
- Default medal definitions are comprehensive with proper rarity distribution.
- The `bIsSecret` flag on NinjaDefuse is a nice touch for hidden achievement systems.

### Score: 6.5/10

## Overall Verdict: NEEDS FIXES

The architecture is sound — clean component design, good struct/enum patterns, proper UE5 conventions for naming and macros, and thoughtful delegate design. However, the broken shuffle algorithm is a **correctness bug** that must be fixed before shipping. The 18-parameter function needs refactoring into a context struct before more medal types are added. Authority checks are essential before any multiplayer testing begins.

**Recommended priority:**
1. Fix shuffle algorithm (Critical — correctness)
2. Refactor CheckForMedals to use context struct (Major — maintainability)
3. Add HasAuthority guards (Major — security)
4. Implement actual Save/Load (Major — functionality)
5. Address remaining minor issues in a cleanup pass
